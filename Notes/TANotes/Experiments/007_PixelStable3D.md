# 007 · Pixel-stable 3D

研究问题：正交相机保持角度与缩放不变时，怎样减少平移导致的像素轮廓变化，同时避免画面按低分辨率像素跳格？

2026-10-04，Minimal 已实现并通过 Unity 验证。属于 [[3D像素风格与程序动画实验路线]] 的第二项，接续 [[006_LowRes3DPixelated]]。本实验研究相机采样稳定性；没有实现 Toon、描边或 t3ssel8r 完整场景的视觉匹配。

场景：`Assets/_Lab/Experiments/007_PixelStable3D/Scenes/007_PixelStable3D_Minimal.unity`。Unity 菜单：`TechArtLab > 007 > Create or Open Minimal`，然后进入 Play。验证菜单：`TechArtLab > 007 > Validate and Capture`，在 Play 的 Game 视图中运行。

## 相机平面的像素网格

设可见源图大小为 $W\times H$，正交半高为 $S$。相机朝向固定时，每个源像素对应的世界长度是：

$$
\Delta=\frac{2S}{H}.
$$

相机的单位右向量为 $r$，单位上向量为 $u$，理想世界位置为 $p$。以世界原点确定网格相位，把位置投影到相机平面：

$$
a=p\cdot r,\qquad b=p\cdot u.
$$

取最近的整格坐标，得到渲染位置 $q$：

$$
q=p+r\left[\Delta\operatorname{round}(a/\Delta)-a\right]
   +u\left[\Delta\operatorname{round}(b/\Delta)-b\right].
$$

只调整右、上两个分量，保留沿相机前方的分量。不能直接对世界 X/Z 取整：等距视角的屏幕方向与世界坐标轴并不重合。也不能把每帧位移先取整再累计，否则慢速位移可能一直被舍去。

默认 $S=4.1$。160×90 时 $\Delta\approx0.09111$，320×180 时约为 0.04556。提高分辨率会缩小取整步长，但也使一个源像素在相同显示面积中占据更少显示像素。

固定角度、缩放与静态模型时，相机在同一网格内移动，$q$ 不变；跨过网格边界，$q$ 改变一个或多个完整像素。这解释了 B 的稳定轮廓和位置跳格为何同时出现。

## 输出补偿与保护边

以源像素为单位记录误差：

$$
e=\frac{1}{\Delta}\begin{pmatrix}(p-q)\cdot r\\(p-q)\cdot u\end{pmatrix}.
$$

最近取整使两个分量都在约 $[-0.5,0.5]$ 内。若相机实际渲染位置偏左，物体在源图里就偏右；显示时需要把图像往左补回。实现采用向右移动采样窗口，等价于把图像向左移动，因此不能反转这个符号。

每侧额外渲染一个源像素作为保护边，完整 RT 为 $(W+2)\times(H+2)$。同时扩大相机视锥：

$$
S_{RT}=S\frac{H+2}{H},\qquad
\mathrm{aspect}_{RT}=\frac{W+2}{H+2}.
$$

这样保护边不会改变每个源像素的世界覆盖范围。中央可见区域仍是 $W\times H$；只扩大 RT 而不扩大视锥会改变场景构图和网格尺度。

C 的 RawImage 采样矩形为：

$$
\mathrm{origin}_{UV}=\left(\frac{1+e_x}{W+2},\frac{1+e_y}{H+2}\right),\qquad
\mathrm{size}_{UV}=\left(\frac{W}{W+2},\frac{H}{H+2}\right).
$$

A、B 使用同一大小但令 $e=0$。保护边覆盖补偿所需的半像素范围，避免边缘采到 Clamp 延展而出现停滞边条。

显示仍为 Point 采样。如果一个源像素放大成 $s\times s$ 个显示像素，C 的可见平移步长约为 $1/s$ 源像素，而不是任意精度的连续运动。例如 4 倍放大时，0.25 源像素的移动可表现为一个显示像素。1 倍显示没有更细的显示网格，补偿优势有限；缩小显示时也不保证像素块等宽。

## 操作与观察顺序

| 操作 | 行为 |
| --- | --- |
| 0 | 三视图比较 |
| 1 / 2 / 3 | 单独放大 A / B / C，同时关闭不用的场景相机 |
| 分辨率按钮 | 160×90、320×180、480×270、640×360 |
| Space | 暂停或恢复自动平移 |
| T | 开关自动平移，从时间零开始 |
| 时间滑条 | 选择固定时间并暂停，便于重复比较 |
| 结果区域右键拖动 | 在相机平面平移；接续当前视图位置并退出自动平移 |
| R | 恢复默认角度、大小、平移原点和自动回放 |
| L | 开关方向光阴影 |
| H | 隐藏或显示文字与按钮，保持结果区域不变 |
| Peak X / Size / Yaw | 水平峰值速度、正交半高、相机方位角 |

默认回放在相机平面运动。设 $v$ 为水平峰值速度，单位是源像素/秒，$\theta=t\,v\Delta/0.65$：

$$
o(t)=r\,0.65\sin\theta+u\,0.24\sin(0.7\theta).
$$

因此回放有减速和反向，面板速度不是整段轨迹的恒定速度。手动平移使用鼠标显示像素位移除以放大倍数，再乘 $\Delta$ 换成世界位移。

1. 保持默认 160×90 和阴影关闭，观察 A 的细杆、石板缝和球轮廓变化，以及 B 的整格移动。
2. 切到 3 放大 C，再切到 2，对照轮廓形状与移动步幅。面板 Output 表示当前实际放大倍数。
3. 暂停后改变角度或缩放，观察轮廓仍会重新采样。停止改变后再平移，网格对齐才重新满足固定条件。
4. 开启阴影，单独观察阴影边界。相机网格不等于阴影贴图网格，不能据此期待所有阴影都稳定。

## 验证与证据

2026-10-04，Unity 6000.6.0f1、URP 17.6.0、Direct3D11、Linear、现有 PC 管线。通过 Unity CLI 创建、导入、编译与运行；Unity 起初未启动，打开现有版本后 CLI 连接正常，没有升级依赖。

本地证据在 `References/007_PixelStable3D/analysis/unity/`，主要报告为 `validation.txt`。稳定性断言使用静态几何、固定正交视角、固定缩放、阴影关闭，RGB 单通道容差为 1/255。图像比较排除外围两像素，平移对照也排除没有对应像素的区域；保护边另作采样范围与世界覆盖检查。

**Verified（Unity）**：相机在同一网格内从 XY=(0.10,0.10) 移到 (0.35,0.35) 源像素位置：

| 可见源图 | A 源图变化像素数 | B 源图变化像素数 | C 在 4 倍放大后对齐一个显示像素的差异数 |
| --- | ---: | ---: | ---: |
| 160×90 | 474 | 0 | 0 |
| 320×180 | 1,049 | 0 | 0 |
| 480×270 | 1,468 | 0 | 0 |
| 640×360 | 1,924 | 0 | 0 |

C 的未对齐图像确实发生移动；移动方向在 X、Y 两轴均正确。B、C 共用源图，因此 C 的变化来自输出采样。

**Verified（Unity）**：X 从 0.49 移到 0.51 源像素、跨越相机取整边界，统一放大 4 倍：B 的变化像素数依次为 16,416、40,416、66,016、90,432；C 的变化像素数依次为 0、0、16、0。480×270 下残留相当于一个源像素的区域；没有声称所有网格边界都逐像素无差异。数值光栅化边界误差是可能原因，但本次没有进一步隔离 GPU 内部精度来源。

**Verified（Unity）**：

- 四档 RT 的保护边保持 $2S_{RT}/H_{RT}=\Delta$；正负残差下的裁剪均在纹理内部。
- 对真实世界标记点比较两台相机的投影，补偿后的误差小于 0.002 源像素。
- 0°、45°、83° 与半高 2、4.1、8 的九种组合中，取整不改变相机深度，残差不超过半源像素。这里检查网格数学，不代表旋转或缩放过程稳定。
- 自动帧与显式相机渲染有 0 个超容差差异像素。
- 实际 Canvas 截图裁剪为 1280×720，即 160×90 的 8 倍放大；与相同 UV 的 Point 裁剪参考有 0 个超容差差异像素，验证了真实显示路径。
- 单视图只启用所需场景相机；布局计算覆盖普通区域与不足源图大小的区域。阴影开关后画面可正常渲染，未据此断言阴影稳定。
- 修改后重新进入 Play 并完成验证。检查中修复了编辑器重载后的 GUI 样式失效，以及退出 Play 时相机先被销毁导致的引用错误；随后通过组件禁用/启用、RT 释放/重建及退出/重入 Play 检查。最终编译正常，当前 Console 无错误、无警告，修复后没有新增错误。资源生命周期记录见 `lifecycle.txt`。

`continuous_source_010/035.png`、`snapped_source_010/035.png` 保存源图对照，`compensated_010/035.png` 保存放大对照，`boundary_049/051.png` 保存 320×180 的边界对照，`canvas_compensated.png` 保存实际屏幕裁剪。`controls_compare.png` 与 `controls_focus.png` 用于操作界面检查。

**Observation（Unity）**：已检查三视图和单视图截图，石柱、球、台阶和细杆可区分，补偿结果保持清楚的像素块。没有自动发送物理键鼠事件；键鼠逻辑通过代码检查，固定状态和渲染结果通过 CLI 验证。窗口适配是布局与当前实际屏幕检查，没有遍历操作系统窗口大小。

## 成本与限制

**Inference / Unity Reproduction Choice**：相机网格计算只有少量向量与取整运算；输出补偿只是更新已有 RawImage 的 UV，不增加一个全屏后处理 Pass。比较模式为了显示 A 与 B/C，绘制场景两次；生产中采用单一方案只需要一台场景相机。单视图虽然只渲染一张图，示例仍保留两张已分配 RT，以便快速切换。

保护边增加少量源像素：160×90 对应约 3.5%，320×180 对应约 1.74%，640×360 对应约 0.87%。这些比例只描述 RT 像素数量，不是实测帧耗时。没有 GPU、CPU 或打包性能基准。

当前只处理静态场景、固定角度与缩放的正交平移。旋转、缩放、透视下不同深度的投影、角色运动与变形、动态光照、阴影级联和透明效果仍可能闪烁，需要各自处理。世界坐标数值过大也会影响取整精度。C 提升平移细度，不恢复低分辨率采样已丢失的细节。

没有本实验新增的原作工程或抓帧证据。t3ssel8r 等作品是学习方向，不将此实现当作对作者全部技术的确认。后续可在保留此 Minimal 场景的前提下，逐项研究 Toon、像素描边、角色运动与光照稳定性。
